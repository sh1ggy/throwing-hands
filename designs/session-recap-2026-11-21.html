01Timeline

Times are commit times. Two commits each landed at 03:02 and 03:27, so they share a dot. Before 03:00 it was hardware work. After that, the server was rebuilt around state machines.

02MCP: Claude writes the rules, the server runs them

Rules are data

A game is JSON. Changing a rule means patching the JSON. No code or firmware changes between games.

Bad edits bounce

A patch is applied whole or not at all. If one is invalid, it's rejected with a message and the running game carries on.

Fair randomness

The server draws numbers and moves. Claude never picks an outcome or judges a camera read.

Replaced along the way: the short-lived "free play" tools (new_game, game_turn…) and freeplay.py were removed on the same day. play_round / play_match stay as the deterministic engine, tagged rps-deterministic.

03State machines: the two fallback games

higher_lower.json · 3 states · the demo's new game

On stage, Claude writes its own version of this from one prompt. This file is the safety net.

rps.json · 13 states · design doc §9.4 round as a machine

Every behaviour test of the old engine has a twin here (26 tests). On the same seeds, engine and machine pick identical moves. Simulator rigged-win reveal lag is 0–1 ms (the limit is 250 ms).

04Player identify: a generic action, game rules elsewhere

  • Game.identify_player is split into scan_faces (facts) and seat_player (RPS rules).
  • identify_player / register_player MCP tools refuse while a machine runs, so the camera never switches mid-game.
  • start_machine('rps', vars={identify: true, check_bribe: true}) gives §9.4's Setup → Idle. An explicit player still overrides the scan.
